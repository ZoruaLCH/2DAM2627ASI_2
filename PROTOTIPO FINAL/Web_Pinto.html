CLAUDE

Lluvia de ideas y Contexto

El proyecto comenzó utilizando Claude como consultor estratégico. Le pedí ideas para una guía de viaje con cuatro niveles de zoom (Instituto, Barrio, Pueblo, País).

Inspiración: Me recomendó webs de turismo (Spain.info, Lonely Planet, Visit London) para inspirar la maquetación.

Contextualización: Le indiqué que el proyecto se centraría en el pueblo real de Pinto (Madrid), aportando enlaces a la Wikipedia y al Ayuntamiento.

CLAUDE

Redacción del Prompt Maestro

Claude redactó un prompt detallado para un "desarrollador front-end senior", especificando las reglas del proyecto:

  • Uso de HTML, CSS y JS puro (sin frameworks).
  • Carga de datos desde un data.json.
  • Uso de Leaflet para mapas interactivos.
  • Maquetación estilo spain.info.
  • Reglas de honestidad: nada de inventar horarios ni precios.

Bloque de fuentes: Se añadió un apartado con todos los enlaces de referencia (Wikipedia, Ayuntamiento, Turismo) para que la IA tuviera contexto real.

GEMINI

Desarrollo de la Arquitectura

Con el prompt listo, pasé a Gemini para programar la base. Se generó una arquitectura profesional separando responsabilidades en 4 documentos:

  • index.html: El esqueleto semántico.
  • styles.css: Variables de tema, responsive, transiciones y modo oscuro.
  • app.js: Carga de datos, estado (favoritos), mapas, búsquedas, quiz y renderizado dinámico.
  • data.json: La base de datos de lugares, eventos y barrios.
PROTOTIPO 1

El Primer Prototipo Funcional

Gemini generó el primer prototipo funcional de la guía. Este primer resultado sentó las bases visuales y estructurales de "Descubre Pinto".

Rediseño: Se cambiaron solo las hojas de estilo para adaptar la maquetación al estilo editorial de spain.info (cabecera blanca fija, hero a pantalla completa, esquinas rectas, paleta rojo/amarillo). El HTML y JS no se tocaron.

Problema detectado: La web salía vacía porque el archivo se llamaba app.json en vez de data.json, y porque fetch() requiere un servidor local (Live Server), no funciona con doble clic.

PROTOTIPO 1

Diferencias respecto a la base generada

Tras probar la base generada por Gemini, se aplicaron los siguientes cambios para llegar al Prototipo 1:

  • Rediseño editorial: Se abandonó el diseño por defecto y se adoptó la estética de spain.info (rojo y amarillo, cabecera fija, tipografía limpia).
  • Contenido real en data.json: Se generó un archivo con 11 lugares, 16 barrios, 5 curiosidades, 4 eventos, 6 fichas de comer/dormir y 4 preguntas de quiz.
  • Corrección de carga: Se renombró app.json a data.json y se estableció el uso obligatorio de Live Server.
  • Depuración inicial: Se corrigieron errores de notificaciones y se ajustó la barra lateral.
DEEPSEEK

El Salto a DeepSeek

Al alcanzar el límite de Gemini, me pasé a DeepSeek para pulir el código, donde surgieron múltiples iteraciones y corrección de errores.

En esta fase se desarrollaron los prototipos 2 y 3, aplicando mejoras estructurales, corrección de bugs visuales y funcionales, y una auditoría profunda del código.

PROTOTIPO 2

Segundo Prototipo (DeepSeek)

Con el sistema de notificaciones operativo y los ajustes de la barra lateral aplicados, se obtuvo el segundo prototipo funcional.

En esta fase se aplicaron mejoras críticas como la sincronización de URL con rutas, la búsqueda global y la protección contra inyección HTML.

PROTOTIPO 2

Diferencias y Mejoras (Prototipo 2)

Comparado con el Prototipo 1, DeepSeek aplicó las siguientes mejoras estructurales:

  • Sincronización de URL: Rutas amigables (ej. #torre-de-eboli) para abrir fichas directamente.
  • Buscador global: Búsqueda en lugares, eventos, barrios y gastronomía, con normalización de acentos (ignorando tildes).
  • Accesibilidad: Uso de aria-label, cierre de menús con Escape y protección contra inyección HTML.
  • Corrección de JSON: El archivo original tenía errores de sintaxis (faltaban arrays como barrios o gastroAndLodging) que bloqueaban la carga.
PROTOTIPO 3

Tercer Prototipo (DeepSeek)

La integración del nuevo acceso rápido al gestor de tareas y las correcciones de estilo dieron lugar al tercer prototipo.

Se resolvieron fallos visuales y funcionales, como el contador inteligente que entiende los meses en español, y se arreglaron los estilos de las tarjetas, modales y mapas.

PROTOTIPO 3

Diferencias y Correcciones (Prototipo 3)

Comparado con el Prototipo 2, se aplicaron las siguientes correcciones y mejoras técnicas:

  • Contador inteligente de eventos: Se reescribió la función initCountdown() para que analice el archivo data.json en busca del próximo evento real. Se añadió un diccionario de meses en español (Ene, Feb, Mar, Abr...) y lógica para calcular los días exactos, saltando automáticamente al año siguiente si la fecha ya ha pasado.
  • Arreglo de estilos CSS rotos: Se solucionó el desbordamiento de las tarjetas horizontales de hoteles y restaurantes ajustando el grid-template-columns. Se corrigieron los iconos de sol/luna del tema oscuro (ahora solo se muestra uno dependiendo del tema).
  • Carrusel profesional: Se ocultó la barra de scroll nativa (fea) y se implementaron flechas de navegación flotantes a los laterales con efectos hover. Además, se ajustó el JavaScript para que el desplazamiento sea suave y preciso.
  • Interacción en mapas Leaflet: Los botones "Ver ficha" dentro de los popups de los mapas no funcionaban debido a la propagación de eventos. Se solucionó usando L.DomEvent.stopPropagation() y delegación de eventos.
  • Rediseño de Modales: Se arregló el posicionamiento de la "X" de cerrar (ahora flota sobre la imagen sin crear huecos) y se estilizaron los botones de "Guardar" y "Compartir" para que sigan la línea visual de la web.
  • Gestor de tareas: Se integró un botón flotante y un panel lateral para la gestión de tareas pendientes (subtareas, progreso, etc.).

Límite de DeepSeek: El menú móvil seguía bloqueado (conflicto de z-index), el style.css estaba duplicado y el scroll se quedaba a mitad de página.

FASE FINAL

La Vuelta a Claude

Debido a la incapacidad de DeepSeek para cerrar los bugs finales, decidí volver a Claude. Al tener una ventana de contexto mucho más grande, pudo solucionar los problemas estructurales.

Corrección del menú móvil: El menú estaba dentro del <header> (que tenía position: fixed; z-index: 1000). Esto creaba un contexto de apilamiento, por lo que la capa oscura (.nav-overlay) quedaba por encima. Se solucionó bajando el overlay a z-index: 999 y usando 100dvh.

PROTOTIPO FINAL

El Prototipo Definitivo

Claude logró unificar el código, limpiar los errores residuales y entregar el Prototipo Final totalmente funcional, estabilizado y con el diseño de Pinto intacto.

Datos actualizados (2026): Se actualizaron estadísticas (habitantes a 56.651 según padrón 2025) y eventos reales del Ayuntamiento (Navidad, Black Friday, Feria del Chocolate).

Mejoras finales: Se añadieron avisos de revisión en el footer, metadatos Open Graph y un favicon con la bandera de Pinto.

PROTOTIPO FINAL

Diferencias y Cierre del Proyecto

Respecto al Prototipo 3, el Prototipo Final presenta las siguientes mejoras definitivas:

  • Estabilidad total: Se resolvieron los conflictos del menú móvil y se unificó el CSS duplicado.
  • Verificación de enlaces: Se comprobó que no quedaran IDs duplicados, que app.js y aparecieran una sola vez, y que la lógica de eventos funcionara simulando fechas reales.
  • Contenido actualizado: Fechas de eventos confirmadas (Black Friday, Feria del Chocolate), fichas de la Torre de Éboli actualizadas y datos de población revisados.
  • Accesibilidad y UX: Se añadió foco visible, reducción de animaciones, y se aseguró que la navegación SPA hiciera scroll al principio de la página.

Tareas pendientes: Verificar coordenadas en OpenStreetMap, rellenar los [COMPLETAR] con datos oficiales y conseguir las fotos definitivas para la carpeta img/.
